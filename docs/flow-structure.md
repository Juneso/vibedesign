# 플로우 구조 규칙 (Booktracking · Release 프로젝트)

> 이 문서는 Release 프로젝트의 **이슈 트리 구조**와 **최상위 플로우 구조도** 규칙의 SSOT다.
> [`LINEAR.md`](../LINEAR.md)의 이슈 작성 규칙(제목·본문 포맷·서브이슈)과 **함께** 적용된다.
> 충돌 시 LINEAR.md의 포맷 규칙이 우선하고, 이 문서는 그 위의 *트리 형태*와 *도표 유지*를 규정한다.

## 1. 이슈 트리 3계층

```
N | 플로우명              ← 최상위 플로우 (예: "1 | 로그인 및 DB")
└─ N-M | 핵심 기획         ← 플로우의 핵심 결정 (예: "1-1 | 로그인 방식 — …")  [라벨: 기획]
   ├─ (UX) 구현 이슈        ← 화면 설계가 핵심                              [라벨: UX]
   ├─ (인프라) 구현 이슈    ← 백엔드·데이터·시스템                          [라벨: 인프라]
   └─ N-M | 하위 기획       ← 더 작은 결정 (필요 시 중첩)                   [라벨: 기획]
```

- **최상위 플로우** `N | 이름` — 사용자 관점의 큰 흐름 하나. 번호는 정수.
- **핵심 기획** `N-M | 이름` — 그 플로우 안에서 "무엇을 어떻게 할지" 정한 결정. `기획` 라벨.
- **구현 서브이슈** — 기획을 실현하는 작업. `UX`(화면) 또는 `인프라`(시스템) 라벨.
- 원칙: **결정(기획)이 위, 그걸 구현하는 UX·인프라가 아래.** 구현 이슈가 어떤 결정을 실현하는지 부모로 드러난다.

### 리프 이슈는 "구현 등급"이어야 한다

이 이슈만 보고 클로드/팀원이 **그대로 구현**할 수 있어야 한다. 리프(구현) 이슈와 데이터 기획 이슈는 다음을 포함:

- **데이터**: 다루는 데이터의 필드·타입·필수여부·기본값·출처 (표로)
- **DB 매핑**: SwiftData `@Model` + Firestore 경로/문서 shape, 다른 데이터와의 관계(FK·1:N·cascade)
- **플로우**: 단계별 동작, 외부 API 매핑(예: 알라딘 응답→모델 필드)
- **검증·엣지 케이스**: 필수값, 중복 방지, 빈 결과·네트워크 실패 처리
- **합격 기준**: 무엇이 되면 끝인지 (관찰 가능하게)
- **미결정**: 확정 안 된 선택지는 기본안+대안을 명시해 남긴다

데이터 모델은 **SSOT 기획 이슈 하나**(예: 서재의 `BKT-329` 책 모델)에 모으고, 화면/구현 이슈는 그걸 참조한다. (서재 `BKT-329`·`BKT-262`·`BKT-330`·`BKT-331`이 이 등급의 기준 예시)

## 2. 라벨 (팀 Booktracking)

| 라벨 | 의미 |
|------|------|
| `기획` | 결정·근거. 보통 핵심/하위 기획 이슈. 근거·탈락옵션은 본문에. |
| `UX` | 화면 설계가 핵심인 이슈 (모달·플로우·입력 화면). |
| `인프라` | 백엔드·데이터 배관 (인증·DB·동기화·삭제 등). |

결정 이슈는 `기획`, 구현 이슈는 `UX`/`인프라`. 라벨 색으로 트리에서 성격이 한눈에 구분된다.

## 3. 최상위 플로우 = 항상 구조도 보유

- **모든 최상위 플로우 이슈(`N | …`) 본문에는 `## 구조 (한눈에)` 섹션과 구조도 이미지가 있어야 한다.**
- **기획이 바뀌면(핵심/하위 기획·구현 이슈의 추가·삭제·의미 변경) 구조도도 갱신한다.** 본문이 SSOT이듯 도표도 SSOT.

### 구조도가 담아야 할 것 (의미 규약)

단순 화면 나열이 아니라, 다음 4가지를 한 장에 담는다:

1. **유저 행동 → 플로우** — 사용자가 무엇을 하면 어떤 흐름으로 이어지는가.
2. **수집 데이터** — 그 행동에서 모이는 데이터의 종류·필드 (예: `Book{제목·저자·표지·ISBN·상태·이유}`).
3. **저장 위치** — 그 데이터가 어디에 저장되는가 (로컬 SwiftData / 클라우드 `users/{uid}/…` 경로).
4. **데이터 간 연관** — 다른 데이터와 어떻게 엮이는가 (1:N, ingest, 개념 공유, 캐스케이드 삭제 등).

권장 레이아웃: **유저 행동 → 수집 데이터 → 저장 & 연관** 3열, 행마다 한 행동을 한 줄로 매핑하고 연관은 화살표·라벨로 표기.
기준 예시: 서재 플로우(`BKT-282`)의 구조도 = `docs/flow-diagrams/flow-2-library.svg`.

### 갱신 방법 (멱등)

1. SVG 소스를 `docs/flow-diagrams/<flow>.svg`에 둔다. (흰 배경 + 인라인 색 = 자립형. 위젯 CSS 의존 금지)
2. 내용이 바뀌면 그 SVG를 수정한다.
3. 렌더 + 업로드 + 본문 이미지 교체를 한 번에:
   ```
   node scripts/flow-diagram.mjs <flowIssue> docs/flow-diagrams/<flow>.svg
   # 예: node scripts/flow-diagram.mjs BKT-259 docs/flow-diagrams/flow-1-login.svg
   ```
   - SVG→PNG(한글 폰트 포함) 렌더 → Linear 업로드 → `## 구조 (한눈에)`의 이미지만 교체.
   - 필요 env: `LINEAR_API_KEY` (`.env.local`, linear-sync와 동일).

### SVG 작성 규약 (자립형)

- `width`/`height` 명시 + `viewBox="0 0 W H"`, 첫 자식으로 흰 배경 `<rect ... fill="#ffffff"/>`.
- 색은 인라인 hex만 (CSS 변수·클래스 금지). 라이트 모드 팔레트 권장:
  - 기획/클라우드 = purple (`#EEEDFE` 채움 / `#534AB7` 선 / `#3C3489` 제목)
  - UX/로컬 = teal (`#E1F5EE` / `#0F6E56` / `#085041`)
  - 인프라/중립 = gray (`#F1EFE8` / `#5F5E5A` / `#444441`)
- `font-family="Apple SD Gothic Neo, sans-serif"` (한글 렌더).

## 4. 보장 장치

- **스킬** [`.claude/skills/flow-diagram`](../.claude/skills/flow-diagram/SKILL.md) — 플로우 작업 시 이 규칙과 갱신 절차를 로드.
- **훅** `.claude/settings.json`의 PostToolUse(`save_issue`) → `scripts/flow-structure-guard.mjs` —
  플로우/기획/UX/인프라 이슈가 저장되면 "도표 최신 여부 확인" 리마인더를 컨텍스트로 주입.
  (비차단. 사용자의 글로벌 훅·husky post-commit과 독립적으로 동작.)

## 5. 기존 규칙과의 양립

- LINEAR.md: 제목 짧은 명사구, 본문 3불렛+콜랩스, 본문=SSOT, 서브이슈 분해 — **그대로 유지**.
  이 문서는 거기에 *트리 번호 체계(N | / N-M |)* 와 *플로우 구조도 의무* 를 더한다.
- husky `post-commit` → `linear-sync.mjs`(커밋→이슈 결과 동기화)와 충돌 없음. 서로 다른 시점·대상.
