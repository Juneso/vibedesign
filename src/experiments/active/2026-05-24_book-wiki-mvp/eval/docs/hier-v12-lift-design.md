# hier-ingest v12 설계 — lift 우선 (구조 먼저, 요약은 부산물)

> 작성: Claude, 2026-08-05 (BKT-342 · 준서 승인). 배경: 피로사회 골든 지도(hier-oracle-피로사회-junseo.md)
> 대조에서 나온 보완점 7가지 + 준서 지시 2건(14종 전체 판정 — 땜질 금지 / API 비용 절감).
> 핵심 반전: 현행 "요약 먼저(메모당 1문장) → 구조 나중(축 판정)"을
> **"구조 먼저(14종 전개 방식 + 슬롯) → 요약은 그 결과"**로 뒤집는다.
> 근거 사례: 짓기와 거주하기 오스만 문단 — 대립 구도(오스만↔앙시앵레짐)를 잡는 순간
> 모든 문장이 이해되고 요약이 나온다 (BKT-346 댓글에 골든 예시 등재).

## 현행의 구조적 문제

14종 전개 방식 판정(relationVocab.mjs)이 **트리 꼭대기(축 편성)에서만** 일어난다.
그 시점엔 재료가 이미 planIngest에서 메모당 요약 1문장으로 뭉개진 뒤다.
→ 관계 축 40~60% "억지"(결함 감사 실측), m95 같은 다개념 메모의 나머지 개념 증발
(나르시스·슬픔·리비도 — 메모에도 런 입력에도 있었는데 트리에서 사라짐, BKT-342 0803 정정 댓글).

## A. lift — 사서(planIngest) 단계 교체

메모(문단) 1건마다 (증분 동화에 그대로 들어가는 단건 연산):

1. **전개 방식 판정**: 이 문단이 14종(relationVocab.mjs) 중 어떤 방식으로 논지를
   전개하는가. 복수 허용. 어휘·정의·오용 금지·검증 질문은 relationVocab에서 주입
   (새 어휘 금지 — 축 판정과 기준 단일 소스).
2. **슬롯 채우기**: 판정한 방식의 MEMBER_SPEC 구조를 채운다.
   - 대조 → { 맞세워진 양쪽, 무엇의 축인가 }  예: 오스만(개인 분리 설계) ↔ 앙시앵레짐(수다 유도 설계)
   - 인과 → { 원인 → 결과 사슬 }
   - 예시 → { 무엇의 사례인가 }
   - 통념 반박 → { 통념, 뒤집는 근거 } …
   슬롯을 채우는 행위가 곧 주장 목록을 낳는다 (준서 요약 3줄과 동형이 되도록 강제).
3. **증거 매달기**: 디테일(카페 테이블·트램)은 주장의 증거로 붙는다. 독립 키워드 금지
   → 신규 키워드 남발(짓기와 거주하기 17개 실측)도 여기서 잡힌다.
4. **표제어**: 각 주장에 2~10자 명사구 표제어 (v9 lift 규칙 계승 — 자구 우선, 합성 금지).

출력 스키마 (주장 단위):

```
Lift {
  memoId,
  claims: [ {
    id, claim,               # 한 문장 주장
    devices: ['대조', ...],   # 14종 판정 (복수)
    slots: { ... },           # MEMBER_SPEC 구조 (쌍·사슬·사례 대상)
    evidence: [ ... ],        # 원문 속 디테일
    headword,                 # 표제어
    confidence                # 낮으면 에스컬레이션 대상
  } ],
  promptVersion               # 프롬프트 버전 — 모델·프롬프트 조합 추적용
}
```

## B. 조립 — 주장 단위로

- **입력 = 주장** (메모 아님). 한 메모의 주장들이 서로 다른 가지로 갈 수 있다 (보완점 ⑦).
- **역할 블록**: lift의 전개 방식 분포로 최상위를 편성 — 통념 반박·문답 계열 = 문제의식,
  인과·분석 = 진단, 해결 관련 = 처방. 대장 1개 독식 금지 (보완점 ①②). LLM 1콜.
- **대조 엣지**: lift 슬롯의 쌍을 그대로 1:1 엣지로. 트리 위 재판정 콜 삭제 (보완점 ③).
- **패러프레이즈 승격**: 표제어 임베딩 클러스터 — "표현 달라도 같은 개념" 2회 이상이면
  키워드 승격. 자구 2회 규칙 대체 (보완점 ⑥). LLM 0콜.
- **묶는 개념(fold-back)**: 여러 블록에 걸친 클러스터(능률·경제 효율·생산 증대)를
  후보로 1콜 판정 (보완점 ④).
- **깊이**: 주장 밀도 따라 자연 비대칭 — 규칙 처리, LLM 0콜 (보완점 ⑤).

## C. 동화(증분)

lift는 단건 연산이라 온라인 패스에 그대로. 폐쇄 판정(attach|new)·통합 패스 구조 유지,
통합 패스에서 역할 블록·fold-back 재계산.

## 비용 전략 (준서 지시 · 0805)

1. **개발 루프 = 로컬 클로드, API 0원.** 피로사회 24메모 lift 정답(lift 골든)을 클로드가
   수동 생성 → 프롬프트가 정답에 수렴할 때까지의 튜닝도 로컬 클로드. 유료 API로 반복 금지.
2. **claude -p transport**: transport 계약이 함수 하나({system,user}→응답)라 헤드리스
   claude CLI 어댑터 추가 — 재생성을 구독 요금 안에서 실행.
3. **배치·판정 = 딥시크**: PROVIDER=deepseek 인프라 재사용 (runLitV1 A/B 구조).
   ⚠ .env.local 에 DEEPSEEK_API_KEY 필요 (현재 이 맥엔 OPENAI 키만 있음).
4. 규모: 피로사회 재생성 1회 = lift 24콜 + 조립 3~4콜. 딥시크 수십 원 / claude CLI 0원.

## 대고객(API) 전환 대비 — 지금 심어두는 것 5가지 (0805 준서 질문)

1. **모델 교체 회귀 테스트 = lift 골든 + 지도 일치 5축.** 후보 모델을 같은 골든에 돌려
   점수 비교만 하면 스왑 판정 완료. "로직 완성 → 모델 갈아끼며 테스트" 전제 조건.
2. **클로드 과적합 방지**: 매 반복이 아니라 **마일스톤마다 1회 딥시크 A/B 체크포인트** —
   모델 간 격차를 마지막이 아니라 조기에 발견.
3. **폐쇄형 설계 = 이식성**: 고정 14종 어휘에서 고르고 슬롯을 채우는 판정은 모델 민감도가
   낮다. 자유 생성 최소화. 확신 낮음 → 상위 모델 에스컬레이션 구조가 그대로 프로덕션
   비용 구조(싼 모델 기본 + 어려운 케이스만 비싼 모델)가 된다.
4. **콜당 토큰·지연 로깅**: 런 로그에 토큰 수·응답 시간 기록 → 모델별 "메모 1건당 몇 원·몇 초"
   단가표가 자동 축적. 온라인 lift 1콜은 수집 UX(BKT-286)와 직결.
5. **프롬프트·어휘의 코드 분리 + promptVersion**: LLM 로직은 전부 백엔드로 간다(BKT-274·372).
   relationVocab 방식대로 프롬프트도 데이터로 분리하고 버전을 달아 이식·조합 추적 가능하게.

## 구현 순서

1. lift 스키마 + 프롬프트 (relationVocab 주입) → 클로드 수동 lift로 피로사회 24메모 골든 생성
2. 조립 수정 (주장 단위 · 역할 블록 · 대조 엣지 · 클러스터 승격 · fold-back)
3. claude -p transport 어댑터 (+ 토큰·지연 로깅)
4. 피로사회 재생성 (일괄 + 동화) → 지도 일치 5축 채점 → **준서 판정**

각 단계 결과는 BKT-342 에 기록하며 진행.
