# /issue-lint <이슈> — 기존 이슈 포맷 검사·수정

새 이슈는 생성 체크리스트가 지키게 하지만, 기존 이슈에 돌릴 진입점이 이것이다.
규칙 SSOT: `~/.claude/conventions/linear.md` — 검사 전에 반드시 읽는다.

## 검사 항목

1. **목표 = 체크리스트** — 마이크로 이슈 단위 `- [ ]`, 진행분은 `- [x]`. 산문 목표는 체크박스로 분해
2. **결과 = 목표의 부연** — 기존 불렛+콜랩스 방식으로, 목표 항목마다 어떻게 끝났나/왜 남았나가 닿는가. 같은 목록을 두 섹션에 반복하지 않는가
3. **섹션 제목 밑 규칙 안내 문구 금지** — "체크박스 하나 = …", "결과와 조응" 류는 삭제
4. **명사형 종결 + 마침표 규칙** — `~한다/~된다/~하세요` 금지, 한 문장 불렛 끝 마침표 없음. 코드 블록·인용 원문은 예외
5. **불렛 3줄 제한** — 배경·작업·결과 각 3줄(목표 체크리스트는 예외). 넘치면 콜랩스로 강등하거나 서브이슈 분해를 제안
6. **콜랩스 제목 = 비개발자 언어** — 파일 경로·API 명은 접힌 안쪽으로
7. **본문 SSOT** — 로그 섹션 없음, Canceled/통합된 이슈를 가리키는 링크 없음, 낡은 수치는 코드와 대조해 정정 제안
8. **결과 콜랩스 상세도** — 산출물·설계 이유·동작·한계 네 가지가 있는가 (완료 이슈만)

## 절차

1. `get_issue` + `linear.md` 읽기
2. 위 8개 항목 위반을 나열 → `save_issue` patch 로 수정 (내용은 보존, 형식만 재배치 — **정보를 지우는 수정은 하지 않는다**)
3. 저장 응답 본문을 훑어 한글 깨짐·중복 헤더·잔여 앵커 확인 (patch 부작용이 잦다)
4. 무엇을 왜 고쳤는지 항목별 보고. 판단이 필요한 것(서브이슈 분해, 낡은 수치)은 고치지 말고 제안

## 하지 않는 것
- Done 이슈 소급 적용 (지시가 있을 때만 — JSN-166 한계 조항)
- 상태 변경 (린트는 본문만)
