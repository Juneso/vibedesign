# /linear-audit <최상위 이슈> — 이슈 ↔ 코드 SSOT 감사

이슈가 말하는 것과 코드가 하는 것이 같은지 확인하고, 어긋난 쪽(대부분 이슈)을 고친다.
근거: JSN-167 (0901 서재·위키 대청소에서 절차 확립). 본문 서식은 `~/.claude/conventions/linear.md` 를 따른다.

## 절차

### 1. 준비
- `git pull` (쓰기 작업 전 필수)
- 최상위 이슈 `get_issue` → 하위를 `list_issues(parentId:)` 로 **재귀** 수집 (본문에 언급만 되고 트리 밖에 있는 이슈도 fetch)
- 이슈들이 주장하는 산출물(파일 경로·커밋 해시·함수명)을 목록화

### 2. 코드 대조
- 산출물 파일이 실제로 있는지 `ls`/`Glob`, 주장하는 동작이 코드에 있는지 `grep`
- 숫자·상수는 실측 (예: "5권" 주장 → 코드의 `prefix(8)` 발견 사례)
- `git log --grep="BKT-XXX"` 로 이슈별 커밋 유무 확인 — **커밋은 있는데 상태가 Backlog/Todo 면 최우선 신호**

### 3. 분류 — 네 가지 어긋남
1. **구현됐는데 미기록** — 결과가 비었거나 상태가 Backlog. 가장 값진 발견 (사례: BKT-330·286·383)
2. **기록이 낡음** — 웹 프로토·구엔진 기준 본문, 폐기된 결정, Canceled 이슈를 가리키는 링크 (사례: BKT-171·287)
3. **목표·결과 미조응** — 목표 체크리스트 없음, 결과가 목표를 부연하지 않음 (`/issue-lint` 기준)
4. **중복·자리 문제** — 같은 내용이 두 이슈에, 또는 별개 이슈일 필요가 없는 것 (→ `/linear-merge` 후보로 보고)

### 4. 고치기 — 이슈 쪽을 수정
- 미기록: `## 결과` 를 산출물·설계 이유·동작·한계 상세도로 채우고 상태를 **In Review** 로 (Done 은 준서 판단이 필요하면 물어본다 — 명시 지시가 있었으면 바로)
- 낡음: 본문을 현행 기준으로 재작성하되 **옛 기록은 지우지 말고** "웹 프로토 시절" 표기로 남기거나 결과 콜랩스로 강등
- 미조응: 목표 체크리스트 + 결과 부연으로 재작성 (섹션 밑 규칙 안내 문구 금지)
- ⚠️ 저장 후 응답 본문을 훑어 **한글 깨짐·중복 헤더·잔여 앵커**를 반드시 확인 — patch 의 replace_range 는 `to` 앵커가 남는다

### 5. 보고
- 어긋남 유형별로 무엇을 고쳤는지 + **플로우 완성까지 남은 일 목록은 기록하지 말고 대화로만 보고** (준서 결정 0901)
- 상태 적체(In Review 오래됨)와 통합 후보는 판단 근거와 함께 제안만

## 하지 않는 것
- 코드 수정 (감사에서 버그를 발견하면 보고만 — 고치라는 지시를 받고 고친다)
- Done 이슈의 소급 포맷 변경 (지시가 있을 때만)
- 남은 일을 새 이슈로 생성 (보고 후 준서가 정함)
